# Time Nickname: время в имени профиля

> автор: @mishabotov · версия 1.0 · `.plugin`, ~630 строк, только Python
> файла плагина в репо нет, здесь разбор и короткие выдержки с указанием автора

плагин раз в минуту (или реже, по настройке) меняет имя профиля, подставляя текущее время. интересен не сам эффект, а то, как аккуратно он работает с сервером: плагин регулярно шлёт `account.updateProfile`, и любой такой плагин быстро упирается во флуд-лимиты.

---

## схема

```text
on_plugin_load ──► _safe_apply(force) через 1.5 с
                         │
                         ▼
_schedule() ── delay до следующей границы (минута/час/сутки) ──► _tick(token)
                         ▲                                           │
                         └──────────── _safe_apply() ◄───────────────┘
                                             │
                                     account.updateProfile
                                             │
                     ┌───────────────────────┴───────────────────────┐
                 ошибка FLOOD_WAIT_N                               успех
          _flood_until = now + N, _schedule()        локально обновить юзера + NotificationCenter
```

## ключевые решения

### 1. ожидание до границы, а не фиксированный интервал

`_next_delay_ms` считает, сколько осталось до следующей «круглой» отметки (начало минуты, часа или суток, в зависимости от формата времени в настройках), и добавляет небольшой запас. благодаря этому имя меняется ровно в 12:00, а не в 12:00:37. если формат содержит только часы, плагин сам переходит на часовой шаг и не тратит запросы впустую.

### 2. токен вместо отмены задач

у `run_on_queue` нет отмены. поэтому каждый вызов `_schedule()` увеличивает `self._token`, а `_tick(token)` первым делом сверяет свой токен с текущим. все старые задачи, запланированные до смены настроек или выгрузки, просто ничего не делают. это самый простой способ сделать «перезапуск таймера» на очереди без отмены.

### 3. запрос с флагом `RequestFlagDoNotWaitFloodWait`

```python
ConnectionsManager.getInstance(int(account)).sendRequest(
    request, wrapper, ConnectionsManager.RequestFlagDoNotWaitFloodWait,
)
```

без этого флага клиент сам ждёт окончания FLOOD_WAIT и держит запрос в очереди. с флагом ошибка сразу приходит в callback, плагин вытаскивает число секунд регуляркой `FLOOD_WAIT_(\d+)`, запоминает `_flood_until` и переносит следующую попытку. `_next_delay_ms` берёт максимум из «до следующей минуты» и «до конца флуда».

### 4. callback держится в списке

обёртку `RequestCallback` плагин кладёт в модульный список `_PENDING_CALLBACKS` и убирает оттуда после ответа. иначе Python-объект может собрать сборщик мусора раньше, чем Java вызовет callback, и ответ просто потеряется.

### 5. привязка к аккаунту по user id

плагин запоминает `user.id`, а не номер слота аккаунта, и при каждом обновлении ищет слот заново через `UserConfig.getInstance(slot).getClientUserId()`. если пользователь переключит аккаунт или поменяет их порядок, время не уедет в чужое имя. исходное имя сохраняется в `base_first_name` / `base_last_name`, есть кнопка восстановления.

### 6. локальное обновление после ответа

сервер не присылает апдейт своего же профиля сразу, поэтому после успешного ответа плагин сам правит `first_name`/`last_name` у текущего юзера и у кэша `MessagesController`, вызывает `saveConfig(True)` и рассылает `mainUserInfoChanged` и `updateInterfaces` с `UPDATE_MASK_NAME`. после этого имя меняется в меню и шапках без перезапуска.

## что взять себе

- токен-паттерн для любых периодических задач на `run_on_queue`;
- `RequestFlagDoNotWaitFloodWait` + разбор `FLOOD_WAIT_N` для всего, что шлёт запросы по таймеру;
- хранение callback'ов до ответа.

> заражённая копия этого плагина гуляет по чатам, см. [security.md](../security.md). в оригинале нет `exec`, base64 и сетевых запросов мимо Telegram.
