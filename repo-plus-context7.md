# репо + context7 — почему при вайбкодинге плагинов лучше использовать их вместе

> короткий ответ: они закрывают разные слои. репо учит нейронку тому, как на практике устроены плагины ExteraGram/AyuGram, а context7 подтягивает свежую документацию по публичным библиотекам, которые ты используешь внутри плагина. вместе нейронка получает и «как у нас принято», и «как сейчас в библиотеке».

---

## что делает context7

context7 — MCP-сервер от Upstash. он подтягивает актуальную документацию и примеры кода по конкретной версии библиотеки прямо в контекст нейронки, чтобы она не опиралась на устаревшие данные из обучения.

как это работает:

- в промпт добавляется `use context7` (или правило в клиенте, чтобы писать это не приходилось)
- нейронка вызывает два инструмента: поиск библиотеки по названию (`resolve-library-id`) и получение её документации
- если знаешь ID библиотеки, можно указать его сразу: `use library /owner/repo`, а версию — через `/owner/repo/v1.0.0`
- работает с Cursor, Claude Code, VS Code, Windsurf и другими MCP-клиентами

что важно знать:

- в индексе должна быть сама библиотека. добавить публичную может **кто угодно** — достаточно вставить ссылку на GitHub-репозиторий на [context7.com/add-library](https://context7.com/add-library)
- в репозиторий можно положить `context7.json` с полем `rules` — это рекомендации для кодинг-агентов, которые подтянутся вместе с документацией
- приватные источники (GitHub, GitLab, Bitbucket, Confluence, OpenAPI и другие) доступны на платных планах

## что даёт это репо

### 1. рабочие примеры кода

готовые `.plugin` файлы. нейронка видит, как реально устроен плагин: как регистрировать хуки, как работать с Java-объектами через Chaquopy, как чистить ресурсы при выгрузке.

### 2. анализы с объяснением «почему»

каждый анализ объясняет не только *что* написано, но и *почему именно так*:

- почему `before_hooked_method`, а не `after_hooked_method`
- почему `getRawX/getRawY`, а не `getX/getY`
- почему токен дедупликации через `getDownTime()`
- почему `run_on_ui_thread` при работе с `View`

с этим контекстом нейронка повторяет рабочие решения, а не просто пишет код, похожий на плагин.

### 3. опыт из практики

разбор конкретных граблей: `AttributeError` из-за обфусцированных имён, R8-лямбды, повторная регистрация хуков после перезапуска. такие вещи обычно живут только в голове разработчика или в рабочем коде.

### 4. подборка источников

в README собраны ссылки на исходники Telegram для Android, декомпилированный ExteraGram 12.5.1 и 12.9.0 (через jadx) и официальную доку по plugin API. репо рассчитан на ExteraGram 12.5.1+ и AyuGram на его основе.

## почему вместе лучше, чем по отдельности

### плагин — это не только plugin API

внутри плагина почти всегда есть и другой код: сетевые запросы, парсинг, работа с файлами, сторонние библиотеки из `__requirements__`. для этой части нужна актуальная документация конкретной версии библиотеки — это как раз то, что делает context7.

### репо отвечает за «как правильно здесь», context7 — за «как правильно там»

| задача | что подключить |
|---|---|
| хуки, `BasePlugin`, `MethodHook`, рефлекшн внутренностей Telegram | репо (примеры + анализы) |
| паттерны, которые уже проверены на практике (дедупликация, кэш reflection, lifecycle хуков) | репо |
| актуальный синтаксис и API стороннего пакета | context7 |
| новая версия библиотеки, о которой нейронка может не знать | context7 |
| исходники Telegram и декомпилированный ExteraGram | ссылки из README репо |

### меньше расхождений в одном промпте

если дать нейронке только репо, она отлично напишет хуки, но для внешней библиотеки будет опираться на то, что помнит из обучения. если дать только context7 — наоборот: свежий API библиотеки и никакого понимания, как устроены плагины. вместе эти две проблемы закрываются одновременно.

### репо можно подключить к context7 как публичную библиотеку

context7 индексирует документационные файлы (`.md`, `.mdx`, `.rst`, `.txt` и т.д.) и вытаскивает из них код и пояснения. исходники вроде `.py` при наличии документации не индексируются, а `.plugin` в этот список не входит.

поэтому в context7 попадут анализы — а в них уже лежат ключевые куски кода с объяснением «почему». сами `.plugin` файлы по-прежнему нужно кидать в контекст вручную. получается разделение труда:

- **context7:** анализы и README, подтягиваются по запросу (`use library /corerudo/for-vibecoders`)
- **вручную:** целиком `.plugin`, который берёшь за образец

в `context7.json` можно положить `rules` — рекомендации, которые context7 отдаёт агенту вместе с документацией.

## как использовать вместе

1. **закинь в контекст файлы из репо:** подходящий по задаче `.plugin` и его анализ (или подключи репо через context7, см. выше)
2. **подключи context7** в своём MCP-клиенте
3. **добавь правило**, чтобы не писать `use context7` каждый раз:

   ```text
   Always use context7 when I need code generation, setup steps, or library documentation.
   Automatically use Context7 MCP tools without me having to ask.
   ```

4. **для внешних библиотек указывай ID напрямую**, если знаешь: `use library /owner/repo` — так нейронка не тратит шаг на поиск
5. **не забудь про официальную доку** — [plugins.exteragram.app/docs](https://plugins.exteragram.app/docs): плагины работают на Chaquopy и Aliucord hook (Xposed-хуки), пишутся на Python 3.11

пример промпта:

```text
напиши плагин по образцу animtou (файлы и анализ выше).
для HTTP-запроса используй httpx — use context7.
```

## вывод

context7 нужен, чтобы нейронка не путалась в версиях и API библиотек. репо нужен, чтобы она понимала, как устроены плагины и почему рабочий код написан именно так. задачи разные, поэтому и подключать лучше оба.

**формула: файлы из репо в контексте + context7 для всего, что за пределами plugin API.**
